No test exceeded 1,280 MiB. This remains an **enforcement/proof gap**, not an

## 1. Current accounting contract

[D21](Invariants.md#d21--persistence-foundation-1) delegates its numeric limits
to PersistenceFoundation1 sections 5–6: 1,280 MiB **directory allocation**,
including database, rollback journal and bounded diagnostics. It explicitly says
the page cap is not a disk quota and requires proof or amendment. This is not
merely the main database's EOF, nor permission to ignore temporary allocations.

The present wording does not define whether shared filesystem metadata, storage
stack copies or deleted-open objects are charged, or which allocation API is
authoritative. This ambiguity is recorded, not silently resolved by choosing the
smallest accounting set. Even the narrower current implementation's allocated-file
measurement lacks a strict in-flight enforcement proof.

| Allocation class | Reachability/accounting finding |
|---|---|
| `store.sqlite3` | Always counted; fixed 4,096-byte pages and 131,072-page maximum. |
| `store.sqlite3-journal` | Count active and retained high-water allocation, even when its header is invalid. Never manually remove it for space. |
| `owner.lock`, legacy `supervisor.lock` | Current preflight accepts these; each EOF <=4,096, observed allocation <=65,536. The worker creates owner.lock; supervisor ownership is otherwise non-filesystem. |
| Diagnostics | Canonical retention <=8 MiB. Current persistence implementation creates no diagnostic files. A future rotating sink would need bounded file count, rotation overlap and allocation accounting. |
| Statement/subjournals, sort/temp B-trees | Potential internal objects, but memory-only under the exact settings/build; no disk temp file in the normal fixed workload. See section 3. |
| Super/master journal | No ATTACH/multiple database commit. No normal creation; startup checks reject a supported super-journal footer reference before SQLite follows it. |
| WAL/SHM | Not generated by normal validated operation. **Reachable on inherited WAL-header startup**, discovered below; cannot simply omit from a universal startup proof. |
| Replacement/copy/recovery files | No application copy, rebuild, rename migration or VACUUM path. Stock rollback recovery operates on existing DB/journal; no separate recovery image. |
| Sparse holes / preallocated extents | EOF and allocated space differ. Writing a hole can allocate without extending EOF. Existing allocated-byte checks are observations, not reservations. |
| Deleted-but-open files | Directory enumeration can miss retained allocation. Normal PERSIST does not unlink its active journal; malformed/incompatible startup and future temporary/rotation paths require separate treatment. |
| Filesystem metadata, extent trees, filesystem journal, virtual-disk backing | File APIs do not report a uniform complete attributable physical footprint. Current wording does not precisely assign these shared costs. |

Unrelated files filling the same disk can cause StorageFull but are not
CarbonLuau-controlled allocation. Offline backup copies are operator-owned.
Another trusted process editing the private files invalidates exclusive-use
premises; it is distinct from CarbonLuau's own allocations. I12 is not an excuse
for an unaccounted SQLite path, erroneous admission or an unexplained result.

## 2. SQLite-native byte-extent proof

Exact pin: SQLite 3.53.4, source ID
`2026-07-24 19:02:57 bf7c7f30031888f4e796e429ab3978879485813aaca6f641c7b33e4e09459bcc`.
The verified amalgamation SHA-256 is
`b1dd5d74ec7f29055a6684fa06fb3c2f6821c87dd38f9a458dfd2e8a1db28189`;
[SQLite.cmake](../native/cmake/SQLite.cmake) records archive/header provenance.
The following line references are to that exact `sqlite3.c`, not floating upstream.

Keep PERSIST, EXTRA, journal_size_limit=-1, cache_spill=OFF, auto_vacuum=NONE,
temp_store=MEMORY, mmap=0, ordinary locking and no chunk-size override. Page size
is already canonical, not implementation-defined. Changing it would change stored
format/geometry and require a migration decision; none is proposed.

| Source evidence | Consequence |
|---|---|
| 65272–65278 | New-page acquisition beyond mxPgno returns SQLITE_FULL. Verify the effective max_page_count, since an existing larger database cannot be capped merely by requesting a smaller value. |
| 65567–65570; 65770–65775 | Start journal at zero; journal only original pages not already in pInJournal. New pages above original DB size are not original rollback records. |
| 65711–65714 | Each page record is page size + 8 bytes. Failure to record membership returns an error, not permission to continue successful mutations. |
| 64317–64345; 66293 | Spill disabled prevents intermediate sync/new-header path; commit uses syncJournal with no new header. |
| 60050; 62392–62404 | Maximum journal sector/header size is 65,536 bytes. Sector-neighbor journaling still stays within original pages. |
| 64015–64019 | Invalidation of a stale following header requires a successful existing eight-byte read; its one-byte write does not extend the old journal. |
| 61034–61064; 61736–61740 | PERSIST invalidates/synchronizes the header; retained EOF is the historical maximum, not cumulative transaction bytes. |
| 61274–61325; 62586–62594; 61987–61989 | First recovery header determines page geometry/original size; later original-size fields do not enlarge the DB; replay pages above the accepted original size are skipped. Existing preflight bounds the first header. |
| 44247–44301; 52418–52434 | Stock SIZE_HINT does not preallocate with chunk size zero and mmap disabled. Unix's mmap branch is a separate reason to retain mmap=0. |

For valid admitted rollback-format states under these constraints:

```text
P = 4,096 bytes; N = 131,072 pages; S <= 65,536 bytes
database EOF <= N * P                     =   536,870,912 bytes
journal EOF  <= S + N * (P + 8)           =   537,985,024 bytes
DB + journal EOF                         = 1,074,855,936 bytes
                                         = 1,025.0625 MiB
+ 8 MiB diagnostics + two 4 KiB locks     = 1,033.0703125 MiB
remaining numerical headroom to 1,280 MiB =   246.9296875 MiB
```

The last two lines are a **byte-length planning calculation**, not a physical
allocation theorem, and diagnostic files do not presently exist. A claimed
less-than-5x physical amplification factor cannot be derived from these numbers.
The ratio also cannot be bounded against *current* live data: a nearly empty DB
can retain a previously full freelist and journal. Use absolute bounds.

Deletes free pages to SQLite's freelist without shrinking the database. Reuse can
avoid growth; fragmentation and larger replacements can still require new pages
and reach FULL before a logical quota is exhausted. The byte quotas are ceilings,
not a promise that every arrangement up to the quota fits. Auto-vacuum changes
page movement/error paths and is excluded, including inherited format state.

`journal_size_limit` is not an active journal cap. Positive trimming adds a
maintenance/commit path and setting zero changes finalization to truncation.
Neither is needed for the retained high-water proof, and neither solves filesystem
allocation. No maintenance is proposed. The [PRAGMA reference](https://sqlite.org/pragma.html#pragma_max_page_count)
and [atomic commit design](https://sqlite.org/atomiccommit.html) provide context;
the exact-pin source and probes provide the bounded-workload evidence.

### Startup exception found by the investigation

An otherwise valid database changed **offline in the disposable fixture** to WAL,
then cleanly closed with no -wal/-shm files, passes initial file preflight. Both
platforms then report `ready=1`, one WAL open and two shared-memory mapping calls
before/while converting to PERSIST. This is not a normal CarbonLuau-generated
state. It establishes an omitted startup file class, **not a cap breach**.

Source: WAL header dispatch 76558–76576, WAL creation 69242–69244, shared-memory
initialization 70183–70248, conversion 104714–104735. Empty WAL has zero frames;
there is no evidence of a database-sized checkpoint copy. One logical SHM region
is 32 KiB on these platforms. Final observer results are recorded below.

The final startup observer sampled after xOpen, xShmMap, xFileControl, xWrite,
xTruncate and xSync: both platforms observed WAL EOF 0, SHM EOF 32,768, conversion
journal EOF 4,616 and peak total allocated-file bytes 49,152. It never observed a
physical-budget exceedance. This small path invalidates a universal “only DB and
journal ever open” statement, not the normal-path page/journal arithmetic.

Required follow-up is a narrow startup-admission audit: exclude unsupported WAL
mode before conversion/auxiliary creation, including page-1 restoration through
hot-journal recovery. A no-hot-journal existing-file gate can check SQLite magic
and header bytes 18/19 equal to 1; that alone does **not** cover arbitrary hot
journals, which can restore page 1. Do not blindly reject every damaged main
header if a normal supported journal can recover it. Qualify incompatible geometry,
auto-vacuum and crafted journal/header combinations separately. Do not enlarge the
production file allowlist or adopt WAL as a shortcut. Production remains unchanged.

## 4. Filesystem findings and candidate elimination

Windows worker: NTFS 3.1, 4,096-byte clusters, 512-byte logical sectors,
4,096-byte physical sectors. Linux named volume: ext4, 4,096-byte statfs unit,
WSL2 `6.18.33.2-microsoft-standard-WSL2`. Block size alone does not prove absence
of bigalloc. No privileged remount, quota, sparse/preallocation policy or volume
configuration was performed.

Windows FileStandardInfo AllocationSize and Linux st_blocks*512 are useful
file measurements, not identical accounting definitions. Microsoft permits
[allocation beyond EOF](https://learn.microsoft.com/en-us/openspecs/windows_protocols/ms-fscc/0201c69b-50db-412d-bab3-dd97aeede13b).
That possibility is not evidence that the fixed SQLite path arbitrarily allocates
it. Conversely, no primary Windows contract inspected here gives the required
maximum transient allocation overhead from bounded writes alone.

ext4 has [allocation clusters](https://docs.kernel.org/filesystems/ext4/bigalloc.html)
and [extent-tree metadata](https://docs.kernel.org/filesystems/ext4/ifork.html).
Upstream Linux 6.18
[getattr](https://github.com/torvalds/linux/blob/v6.18/fs/ext4/inode.c#L5770-L5793)
also includes delayed-allocation reservations in st_blocks. That source explains
why the measurement is not simply already-materialized sectors; it is not an
audit of every patch in the exact WSL kernel. Metadata sharing and the virtual
disk add attribution questions below the file API. Sparse writes, hole filling
and filesystem allocation do not become bounded merely because EOF did not grow.

Evaluate the requested candidates in order:

| Candidate | Verdict |
|---|---|
| A — static SQLite bound | Establishes DB/journal byte extents for validated states. Cannot close the physical step without a separately proved filesystem overhead bound; inherited startup also needs tightening. Preferred building block, insufficient for the original guarantee. |
| B — native bounds plus maintenance | Retained high-water is already bounded. Trimming/compaction does not establish physical overhead and can add temporary allocation/durability paths. Reject as a solution; no VACUUM introduced. |
| C — small policing VFS | Can reject requested extent growth, but cannot turn a pre/post allocation query into a physical reservation. Would need xOpen/xClose/xDelete, xWrite, growth/truncation, xFileControl/SIZE_HINT, shared-memory allocation, temp files and retained/deleted-handle accounting. Writes into holes matter even below EOF. The filesystem premise remains. Not implemented or recommended. |
| D — explicit allocation-contract amendment | **Recommended**: preserve hard logical/byte-extent controls, make the physical budget's conditional/observational nature explicit. Requires user approval; not 1A PASS. |

A VFS rejection before a write may return SQLITE_FULL; partial I/O, rollback I/O,
sync and commit-marker failures require the existing stronger uncertainty rules.
Any future VFS must preserve stock locking/sync ordering and single-worker-thread
serialization. It must not call Lua/managed code recursively. A fixed-preallocated
container with its own logical EOF, recovery and allocation geometry is a larger
storage format/VFS redesign, not a small quota wrapper. See SQLite
[I/O methods](https://sqlite.org/c3ref/io_methods.html) and
[allocation hints](https://sqlite.org/c3ref/c_fcntl_begin_atomic_write.html).

Preflight checks remain valuable for oversized/preallocated/incompatible files and
headroom admission, but check-then-write is not enforcement. Even exclusive worker
ownership cannot remove allocations made by its own later filesystem calls.
Postflight detection cannot retroactively prevent a transient peak or undo a commit.

### OS quota/deployment mechanisms

- [NTFS quotas](https://learn.microsoft.com/en-us/windows/win32/fileio/disk-quota-limits)
  charge data-stream lengths by owning SID/volume, not all physical metadata. They
  also encompass unrelated files owned by that SID; not a self-contained directory cap.
- ext4 project quotas require filesystem/admin configuration. A direct 1,280-MiB
  setting is not a complete proof for all metadata: upstream
  [reservation code](https://github.com/torvalds/linux/blob/v6.18/fs/ext4/inode.c#L1511-L1522)
  and [metadata allocation](https://github.com/torvalds/linux/blob/v6.18/fs/ext4/balloc.c#L699-L705)
  permit metadata charging without failure in a delayed-allocation case. Exact
  accounting plus a proved allowance would require separate qualification.
- [Docker volumes](https://docs.docker.com/engine/storage/volumes/) are not inherently
  size-limited. Container writable-layer limits do not constrain a separate named
  volume. A sparse virtual disk's virtual capacity is not its host physical footprint.
- A dedicated non-growing block volume can bound its own addressable capacity,
  including internal metadata, but requires deployment administration and full-volume
  recovery qualification. File-backed/container metadata outside it needs separate
  accounting. This is not proposed for ordinary default deployments and was not created.

Thus no simple self-contained supported mechanism examined here establishes the
original portable physical guarantee. This is not a theorem that no specialized
filesystem integration could ever do so. The proposed amendment is acceptable for
ordinary Windows/Linux installations **only if the operator accepts loss of the
strict physical quota**. If that remains mandatory, approval must be withheld;
an OS-enforced deployment/storage design needs separate work.

### Failure, corruption and recovery

Definite pre-COMMIT FULL plus successful rollback/autocommit confirmation may
return StorageFull and continue if healthy; do not classify ordinary exhaustion
as corruption. Preserve atomic value/quota accounting. COMMIT failure, lost
acknowledgement or post-commit allocation-check failure remains Indeterminate;
never replay or claim rollback/exactly-once. SQLite
[transaction error handling](https://sqlite.org/lang_transaction.html) requires
distinguishing automatic whole-transaction rollback from a still-active transaction.

Preserve corrupt/incompatible/over-budget data and journals for operator action.
No automatic deletion, truncation, reset, quota reconstruction or copy-overwrite
to regain space. SQLite's normal qualified journal recovery is different from
application destructive repair. The two cap-crash cases at 512 MiB verified
accounting consistency after recovery; they do not prove every malformed journal.
