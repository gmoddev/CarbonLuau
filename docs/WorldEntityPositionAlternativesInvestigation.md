## Qualified host phase versus a phase name

`ServerMgr.Update` `0x06007a9f` conditionally calls `Physics.SyncTransforms`
at `IL_022c` according to physics synchronization settings, then performs other
systems. `LateUpdate` `0x06007aa0` flushes network connections; `FixedUpdate`
`0x06007aa1` calls mountable/buoyancy cycles. Matching Windows/Linux managed
bodies do not supply a universal all-Transform job-completion barrier.

The exact PhysicsModule `Physics.SyncTransforms`, token `0x06000347`, is an
internal call on both platforms. Unity describes it as flushing Transform changes
to physics, including relevant Rigidbody/Collider state—not a universal bounded
job-read lease. [Physics.SyncTransforms reference](https://docs.unity3d.com/6000.3/Documentation/ScriptReference/Physics.SyncTransforms.html).
Explicitly invoking a global flush/Complete would also charge its potentially
population/dependency-sized work to the caller; moving it out of the query does
not by itself qualify CarbonLuau-owned bounded snapshot maintenance.

End-of-frame rendering callbacks do not establish this theorem either. Their
documented purpose is rendering/coroutine ordering, not bounded completion of
every entity's dependencies. The batch-mode restriction in Unity's WaitForEndOfFrame
documentation is specifically about the **Editor**; it is not asserted here as
proof that a dedicated Player callback cannot run.
[WaitForEndOfFrame reference](https://docs.unity3d.com/6000.3/Documentation/ScriptReference/WaitForEndOfFrame.html).

## Bounded batch/snapshot jobs: position kernel versus acquisition

Independent exact-native review establishes a useful positive distinction:
selected-descriptor sorting/grouping and dependency gathering do not inherently
scan every hierarchy node. An already-bound, clean asynchronous Transform job can
forward dependencies rather than synchronously Run them. Inside an actual,
qualified Transform-job access lease, a custom evaluator limited to D ancestor
steps could compute root position in O(M(D+1)) for M selected descriptors, or
fail the whole query if the depth/validity envelope is exceeded.

That is **not** a qualified end-to-end primitive. Merely calling ordinary
TransformAccess.position inside the job leaves its uncapped ancestor walk.
Read-only producer work-stealing, owner polling, binding, scheduling, completion
and reclamation are separate terms. Native addresses below are ELF virtual
addresses / PE RVAs, never raw file offsets or runtime call targets.

| Exact path | Established issue |
|---|---|
| Linux array replacement `0xd2a230`, wait `0xd2a280` | Prior represented hierarchies can be completed before bindings are removed. |
| Linux handle append `0xd2a2e0` -> `0xd26ab0`, wait `0xd26ac8` | Selected-handle resolution can wait for its hierarchy dependency **before** the asynchronous reader is scheduled; object resolution also uses `0xd14440`. One shallow selected entity does not bound the work of its enrolled job. |
| Linux preparation `0xd292f0`, wait `0xd29322`; Windows `0x671930`, wait `0x671986` | Dirty array preparation can complete the previous array job. Selected sorting may be boundable; this wait is not bounded by selected count. |
| Linux schedule `0xc0ce50` -> `0xc00260`; Windows `0x56b340` -> `0x5606c0` | Conditional reflection-helper fence wait requires separate qualification; async mode does avoid the Linux Run-mode wait at `0xc0cfec`. |
| Linux scheduling allocator `0xc0c590` -> `0xc02f90` -> `0xc055b0` -> `0xc07800` -> `0xc07490` | Under pressure, calls helper execution at `0xc07719` -> `0xc08cb0`, pauses, then retries at `0xc074e0`. No selected-count/depth limit bounds unrelated helped work or retries. |

The main task cross-checked the Linux selected-handle dependency branch,
allocation helper/retry and Windows dirty-preparation wait with the existing
read-only PE/ELF decoder. No native addresses were invoked or patched.
These are actual branches outside an M/D-only bound, not a claim that arbitrary
CLR concurrency defeated a getter guard in a live test.

## Broader changes realistically available

The completed-Spawn catalog remains the smallest membership substrate. The
following are specific position/resource changes, not a renewed spatial-index
design or generic query engine:

1. **Reusable capped Transform arrays and incremental binding.** Amortizes selected
   sorting and avoids repeated per-query array replacement. It still must bind
   newly spawned/reused slots and deal with prior dependencies, queue allocation,
   producer work and teardown. Moving a waiting bind to Spawn would violate the
   already-qualified constant bounded observer work. Moving it to maintenance
   merely shifts the same bound unless try-admission is established.
2. **Host/engine-owned bounded snapshot-job admission.** The promising stronger
   route: reserve a fixed pool of descriptors, dependency/job registrations and
   result records; finite try-admission rather than queue helping/retry; capture
   and publish dependencies under the engine's actual access protocol; capped
   ancestor evaluation; bounded non-flushing completion/reclamation. It needs an
   exact engine-supported resource/access primitive, not removal of existing waits.
   No such callable public bounded-admission primitive was qualified here. Private
   stripped-function patching is not silently adopted as that protocol.
   The inspected native allocator does have an indirect callback/exit branch at
   `0xc076e8` -> `0xc0779b`, but its cleanup includes another CAS retry loop at
   `0xc077c0`. That is not itself a bounded try-admission API. The pinned managed
   `JobsUtility.JobScheduleParameters` exposes only Dependency, ScheduleMode,
   ReflectionData and JobDataPtr, not this allocator callback or a reserved-resource
   contract. Calling an internal address with an inferred signature is not adoption.
3. **Host-supported finite try-read lease.** An upstream/exact-host helper could
   atomically acquire stable hierarchy/dependency access and compute at most D
   ancestor steps without a waiting getter. Pending/conflicting work fails the
   **whole query**, never produces a subset. This is an engine access adaptation,
   not another uncoordinated before/after guard. Current public APIs do not establish
   it; symbols/source alone would still require a correctness/work proof.
4. **New universal host scalar snapshots.** A host-owned producer could supply
   exact epoch/position/sample authority for all Entities. Existing player/network/
   physics caches are not that producer. A CarbonLuau-owned bounded catalog walk
   refreshing scalars still needs one of the bounded read/acquisition mechanisms
   above; a global waiting refresh is not a solution. Snapshot sampling semantics
   must be explicit and separately justified.

If jobs are used, hard capped retained job data can prevent unbounded memory
growth when delivery authority retires, but it does not make Schedule bounded or
cancel an already-running engine job. Callback references must release on retirement;
result/native storage cannot be freed while still in use. Resource limits must
remain bounded **across plugin reload generations**, not only per instance.
Exact original epoch/weak candidate identity and owner-thread lifetime revalidation
must accompany every sample; no slot/ID/package retargeting is permitted.

Waiting for a better moment, retrying until quiescent, omitting difficult candidates,
using a player/physics subset, arbitrarily old caches, worker-thread Unity getters,
or completing all world work synchronously are not adopted fallbacks. A phase
snapshot does not freeze future movement. No new public signature or freshness
promise is assigned by this investigation.
